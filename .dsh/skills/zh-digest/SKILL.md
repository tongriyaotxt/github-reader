# 给日报补中文摘要

**这个 skill 只做一件事：跑一条命令，然后验证结果。** 翻译本身由 `ghdigest --zh` 内部的
LLM 调用完成，格式、批量、解析、写回全部是确定性代码。你不要手动改日报文件。

## 步骤

### 1. 跑

```bash
cd <仓库目录>
python -m ghdigest --zh-only          # 只翻译已有日报，不重新抓取（快，省配额）
python -m ghdigest --zh               # 完整流程：抓取 + 生成 + 翻译
```

日报已存在、只是缺中文时**一律用 `--zh-only`**。重跑完整流程会重新抓取，
多花 ~105 秒和 ~450 次 GitHub 配额，而你要的结果完全一样。

### 2. 验证完成

**完成判据：再跑一次，命令报 `待翻译 0 条`。**

```bash
python -m ghdigest --zh-only
```

这是自验证的——比数行数可靠。别用 grep 数 `**一句话**` 的行数：速览条目有
两格缩进，而且同一仓库可能同时出现在精选和速览两处，数出来的数字对不上是正常的。

命令退出码为 0 **不等于**翻译完整：翻译分批进行，单批失败只影响那一批，
其余照常写入。

### 3. 有缺口就重跑

```bash
python -m ghdigest --zh-only
```

**重跑安全且幂等**：已翻过的条目会被识别并跳过（两阶段扫描，不依赖行序），
只补缺失的那些。所以处理缺口就是"再跑一次"，不需要任何手工修补。

## 边界

**不要手工编辑 `digests/*.md`。** 译文由 `parse_digest` / `apply_translations`
按固定规则插入，手工改动会让后续重跑的对齐失准。

**不要翻译 `**建议**` 字段。** 它由工具生成，本来就是中文；翻译它只会得到
逐字重复的两行（这个 bug 真发生过）。

**译文质量不满意时**，改的是 `ghdigest/translate.py` 里的 `SYSTEM_PROMPT`，
不是某一份日报里的那句话——改 prompt 才会对以后所有日报生效。

## 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| `没有可用的 API key` | 凭据缺失 | 读 `~/.dsh/.credentials.yaml` 的 `DEEPSEEK_API_KEY`；或设 `DEEPSEEK_API_KEY` 环境变量 |
| `待翻译 0 条` | 已全部翻过 | 正常，无事可做 |
| 某批失败 | 网络抖动或限流 | 直接重跑；单批失败不影响其它批 |
| 译文明显出错 | prompt 或模型问题 | 改 `SYSTEM_PROMPT`；`--zh-model` 可临时换模型 |
| 想全部重翻 | 需要清掉已有译文 | 删掉日报里的 `**一句话**：*` 行后再跑 |

## 为什么是这个设计

工具零依赖、免费、可复现地做结构性工作（抓取、筛选、排序、上手成本评估），
中文这一步才引入 LLM——因为只有它非 LLM 不可。

中文写成**新增字段**而不是替换英文原文，所以：
- 英文原文永远在，日报可随时重新生成而不丢信息
- 译文可以单独重跑，不必重跑抓取
- 译文出错时能对照原文排查

验证这一点：`python tests/test_translate.py`（25 个测试，守着"翻译不得改动
任何机器提取的数据"和幂等性这两条不变量）。
